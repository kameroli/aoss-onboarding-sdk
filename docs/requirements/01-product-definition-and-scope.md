# Onboarding SDK Requirements — Product Definition and Scope

**Document:** SDK-REQ-01 | **Maps to:** Application Outcome & Status Standard v0.1 (SPEC.md, openapi.yaml) | **Status:** Draft | **Date:** September 1, 2026 | **Rev:** 3 (Rev 2: terminology aligned to AOSS SPEC.md; contact verification re-scoped to institution-side. Rev 3: reconciled to `openapi.yaml` v0.1.0 — email required/phone optional per the `Applicant` schema; resumability split into post-submission (server state) and pre-submission (host `DraftStore`))

## 1. Problem statement

Digital account-opening and credit-application journeys at U.S. financial institutions are assembled per institution from a shifting set of internal and third-party systems, identity verification, document verification, fraud screening, bureau pull, decisioning, each of which reports progress and outcomes in its own vocabulary. The mobile front end absorbs that inconsistency: applicants see statuses that don't map to a clear next step, errors that don't say what to do, and outcomes they can't interpret, and each institution rebuilds the same screens, validation, disclosure sequencing, consent evidence, accessibility work, and localization independently and divergently. The SDK specified here removes that duplicated, divergent front-end layer by providing configurable native iOS and Android flow components that render one canonical status and error model (the Standard) supplied by a middle layer, so that an adopting institution configures a deposit or credit-card onboarding flow rather than building one, and every applicant, regardless of institution, vendor stack, language preference, or assistive technology, receives a consistent, resumable, explainable application journey.

## 3. Scope

### 3.1 Scope principles

- **v0.1 (MVP)** proves the mechanism: one applicant, two product flows, every canonical status rendered, resumable, accessible, bilingual, vendor-agnostic. It is a reference implementation an adopter can evaluate and an author can demonstrate, not a general-availability product.
- **v1.0** adds the steps most institutions require for production launch and which each introduce a new vendor class or a new regulatory mechanism.
- **Post-v1** covers alternate applicant structures, alternate channels, and tooling.
- Items marked **Never** are structurally outside the SDK's remit: the SDK renders and evidences; it does not decide, verify, or author legal content.

## 4. Non-goals (explicit)

- The SDK does not shorten, replace, or make representations about any institution's compliance program.
- The SDK does not guarantee approval rates, completion rates, or decision times; it makes them measurable and consistent.
- The SDK does not impose a visual brand; it imposes layout, hierarchy, accessibility, and behavior.
- The SDK does not communicate with any vendor directly.

## 6. Success criteria and instrumentation

No target values are stated. Each criterion is defined as a measurable quantity and the instrumentation that produces it. Event names are provisional and will be finalized in the event catalog published with the screen-level specifications.

| ID    | Criterion                              | Definition                                                                                                                                                                                                                           | Instrumentation                                                                                                                           | What the institution must join                                                                                |
| ----- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| SC-01 | Application completion rate            | Applications reaching `submitted` / applications reaching `started`, per product, per platform, per language                                                                                                                         | `application.started`, `application.submitted` with `application_id`, `product_type`, `platform`, `locale`                                | Nothing                                                                                                       |
| SC-02 | Step-level drop-off                    | For each step: `step.exited` without `step.completed`, attributed to the last visible state (validation error, blocking error, user back, backgrounded)                                                                              | `step.viewed`, `step.completed`, `step.exited` with `step_id`, `exit_reason`, `last_error_category`                                       | Nothing                                                                                                       |
